# 通用 PR 模板

> PR-only 分支模型下合并纪律的载体。工单 PR 目标 `develop`，发布 PR 目标 `main`。硬字段空着不许合；软字段填「无」须附理由（裸「无」/「略」/「正常」打回）。

```markdown
## 对应分支与工单
<!-- 源分支 → 目标分支 + 关联工单号。工单 PR 目标 develop；发布 PR 目标 main。【硬必填】 -->
________ → develop
工单：#________（无则填「无」）

## 发布 PR 必填（目标 main 的 develop→main 发布 PR 才填，其余填「不适用」）
<!-- 发布 PR 一律人工审合。以下字段硬必填，空着不许合 -->
本次包含工单：________
测试记录（测了什么、结果如何）：________
发布闸自检（develop 不落后 main）：是 / 否

## 改动类型
<!-- feat / fix / refactor / docs / chore。【硬必填】 -->
________

## 实现范围
<!-- 目标 + 边界 + 具体改了啥。【硬必填】 -->
________

## 关键文件
<!-- 核心改动文件路径，每行一个。【硬必填】 -->
- ________
- ________

## 设计决策
<!-- 为啥这么做 + 考虑过的替代方案。trivial 改动填「无：<理由>」 -->
________

## 业务规则
<!-- 涉及的领域约束：状态机/权限/数据约束。纯技术改动填「无：<理由>」 -->
________

## 已知风险
<!-- 已知未解决的问题/潜在影响。无则填「无：<理由>」 -->
________

## 测试结果
<!-- 跑了啥自测 + 覆盖范围（typecheck/lint/单测/手测）。【硬必填】 -->
________

## 相关测试用例
<!-- 关键用例：边界值/等价类/异常路径，每行一个。无则填「无：<理由>」 -->
- ________
- ________

## 边界条件审查重点
<!-- 请审查者重点盯的边界（null/0/负数/并发/权限）。审查者须逐条核对，不是摆设 -->
________

## 未完成事项
<!-- TODO / 后续 follow-up。无则填「无：<理由>」 -->
________
```

## 审查者注意

- 发布 PR（develop→main）：一律人工审合，核对工单列表与测试记录，确认发布闸自检通过。
- 软字段（设计决策/业务规则/已知风险/用例/边界条件/未完成）填「无」须附理由。
- 「边界条件审查重点」段是请审查者逐条核对的内容，不是摆设。
