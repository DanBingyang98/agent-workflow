# UI 原型（UI Prototype）

在单个路由上生成**几个差异极大的 UI 变体**，用悬浮底栏切换。用户在浏览器里翻变体、挑一个（或从每个里偷几块），然后把其余扔掉。

如果问题关于逻辑/状态而不是外观——走错分支了。用 [LOGIC.md](LOGIC.md)。

## 什么时候是这个形态

- 「这个页面应该长什么样？」
- 「定下来之前我想看看这个 dashboard 的几个选项。」
- 「给设置界面换个布局试试。」
- 任何用户本来会在脑子里三个模糊 mockup 之间纠结一整天的时候。

## 两个子形态——强烈优先子形态 A

UI 原型**紧贴应用其余部分**时容易判断得多——真实 header、真实 sidebar、真实数据、真实密度。一个孤零零的临时路由是真空：每个变体孤立看都还行。只要有一个像样的现有页面可以承载变体，默认用子形态 A。只有原型真的没有就近的家时才用子形态 B。

### 子形态 A —— 对现有页面的调整（首选）

路由已存在。变体渲染在**同一路由**上，由 `?variant=` URL 查询参数门控。现有数据获取、参数、认证全部保留——只换渲染。这是默认；没有具体理由就别换。

如果原型针对的东西还没有页面，但*自然应该住在某个页面里*（dashboard 的新区块、设置屏的新卡片、现有流程的新步骤）——那还是子形态 A。把变体挂进宿主页面。

### 子形态 B —— 新页面（最后手段）

只有被原型化的东西真的没有现有页面可以住进去时才用——例如全新的顶层界面，或无法嵌入任何合理位置的流程。

遵循项目已有的路由约定创建**临时路由**——不要发明新的顶层结构。命名要明显是原型（例如路径或文件名里带 `prototype`）。同样的 `?variant=` 模式。

在定下子形态 B 之前做一次 sanity check：真的没有现有页面能嵌入吗？空路由会藏起充实路由才能暴露的设计问题。

两个子形态的悬浮底栏完全相同。

## 流程

### 1. 写下问题并选 N

默认 **3 个变体**。超过 5 个就不再是差异极大而是噪音——封顶。

用一行写下计划，放在原型位置或文件顶部注释：

> "Three variants of the settings page, switchable via `?variant=`, on the existing `/settings` route."

无论用户在场反对与否都这么做。

### 2. 生成差异极大的变体

起草每个变体。每个都守住：

- 页面的用途和它能访问的数据。
- 项目的组件库 / 样式系统（TailwindCSS、shadcn、MUI、纯 CSS，随便什么）。
- 清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构不同**——不同布局、不同信息层级、不同主要操作面，不只是不同颜色。三个微调过的卡片网格不是 UI 原型，是壁纸。如果两个草稿太像，用明确的「不要用卡片网格」约束重做一个。

### 3. 接起来

在路由上创建单个切换组件：

```tsx
// 伪代码——适配项目框架
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（现有页面）：在切换器上方保留所有现有数据获取；只有渲染子树随变体变化。

子形态 B（新页面）：`/prototype/<name>` 下的临时路由挂同一个切换器。

### 4. 构建悬浮切换器

屏幕底部居中的小固定条，三块：

- **左箭头** —— 循环到上一个变体（环绕）。
- **变体标签** —— 显示当前变体键，如果变体导出了名称也显示它。例如 `B — Sidebar layout`。
- **右箭头** —— 向前循环（环绕）。

行为：

- 点箭头更新 URL 查询参数（用框架的路由器——Next 用 `router.replace`、React Router 用 `navigate` 等），让变体可分享、刷新后稳定。
- 键盘：`←` 和 `→` 方向键也能循环。当 `<input>`、`<textarea>` 或 `[contenteditable]` 聚焦时不要拦截方向键。
- 视觉上与页面区分（例如高对比药丸、微阴影），明显不是被评估设计的一部分。
- 生产构建中隐藏——用 `process.env.NODE_ENV !== 'production'` 或等价检查门控，让误合并的原型无法把底栏发给用户。

把切换器放进单个共享组件，让两个子形态都能复用。放在项目共享 UI 所在的地方。

### 5. 交付

亮出 URL（和 `?variant=` 键）。用户有空就翻。有趣的反馈通常是**「我要 B 的 header 配 C 的 sidebar」**——那才是他们真正想要的设计。

### 6. 沉淀答案并清理

某个变体胜出后，沉淀答案——哪个变体、为什么——然后按 [SKILL](SKILL.md) 描述的方式沉淀原型。把赢家折进真实代码，其余放上临时分支，不进 main：

- **子形态 A** —— 把赢家折进现有页面；把输掉的变体和切换器移出 main。
- **子形态 B** —— 把赢家提升为真实路由；把临时路由和切换器移出 main。

完整变体集合是一手来源，所以它落到临时分支而不是垃圾箱——留在 main 分支的变体组件和切换器腐烂很快，还会迷惑下一个读者。

## 反模式

- **只在颜色或文案上不同的变体。** 那是微调，不是原型。真正的变体在结构上分歧。
- **变体间共享太多代码。** 共享 `<Header>` 可以；共享 `<Layout>` 就废了意义。每个变体都应该能自由扔掉布局。
- **把变体接到真实变更上。** 只读原型没问题。如果变体需要变更，指向 stub——问题是「应该长什么样」，不是「后端好不好使」。
- **把原型直接提升到生产。** 变体代码是在原型约束下写的（无测试、最小错误处理）。折进去时要正经重写。
