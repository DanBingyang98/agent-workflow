# 原型（Prototype）

原型是**用来回答问题的临时代码**。问题决定了它的形态。

## 选择分支

确定要回答的问题——从用户的提示、周围代码中判断，或如果用户在场就直接问：

- **「这套逻辑 / 状态模型感觉对吗？」** → [LOGIC.md](LOGIC.md)。构建一个可分享的单个 HTML 文件——自由点击按钮加分页的引导式演练——把状态机推向纸面上难以推理的用例，让非开发人员也能操作。
- **「这个应该长什么样？」** → [UI.md](UI.md)。在单个路由上生成几个差异极大的 UI 变体，通过 URL 查询参数和悬浮底栏切换。

两个分支产出完全不同的东西——选错会浪费整个原型。如果问题确实模糊且用户不可联系，则默认选择与周围代码更匹配的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明该假设。

## 两个分支都适用的规则

1. **从第一天起就是临时的，并明确标注。** 把原型代码放在靠近实际使用位置的地方（要为之做原型的模块或页面旁边），让上下文显而易见——但命名要让读者一眼看出是原型而不是生产代码。临时 UI 路由要遵循项目已有的路由约定，不要发明新的顶层结构。
2. **运行成本趋近于零。** UI 原型用项目任务运行器中的一条命令启动——`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示是用户双击即可打开的单个 HTML 文件。无论哪种，启动都不需要思考。
3. **默认不持久化。** 状态只存在于内存中。持久化是原型要**验证**的东西，不是它应该依赖的东西。如果问题明确涉及数据库，就用一个带「PROTOTYPE — wipe me」之类明确名称的临时 DB 或本地文件。
4. **跳过打磨。** 不写测试，错误处理只做到让原型**可运行**为止，不写抽象。重点是快速学到东西。
5. **暴露状态。** 每次动作后（逻辑）或每次切换变体时（UI），打印或渲染完整的相关状态，让用户看到什么变了。
6. **完成后沉淀。** 把验证过的决策折进真实代码，然后把原型本身作为**一手来源**保存：提交到一个临时分支（不进 main），并在实现 issue 上留下指向该分支的上下文指针。答案也要沉淀——结论和它回答的问题——写进 issue 或一次提交。main 分支只保留验证过的决策。
