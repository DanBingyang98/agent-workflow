# Diagnosing Bugs（诊断 Bug）

一种针对疑难 bug 的纪律。只有明确理由才能跳过阶段。

探索代码库时，读取 `CONTEXT.md`（如果存在）以获得相关模块的清晰心智模型，并检查所触及区域的 ADR。

## 阶段 1 —— 构建反馈回路

**这才是技能本身。** 其它一切都是机械动作。如果你有该 bug 的**紧密**通过/失败信号——一条能在这个 bug 上变红的命令——你一定能找到原因；二分、假设检验、插桩都只是消耗它。如果没有，盯再多代码也救不了你。

在这里投入不成比例的努力。**要激进。要有创造力。拒绝放弃。**

### 构建回路的办法——大致按这个顺序试

1. 在能触及 bug 的任何接缝写**失败测试**——单元、集成、e2e。
2. 对着运行中的 dev server 写 **curl / HTTP 脚本**。
3. 用 fixture 输入做 **CLI 调用**，把 stdout 与已知良好的快照 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，断言 DOM/console/network。
5. **回放捕获的 trace。** 把真实网络请求 / payload / 事件日志存盘；通过隔离的代码路径回放。
6. **临时 harness。** 启动系统的最小子集（一个服务、mock 依赖），用一次函数调用驱动 bug 代码路径。
7. **属性 / fuzz 循环。** 如果 bug 是「有时输出错」，跑 1000 个随机输入，找失败模式。
8. **二分 harness。** 如果 bug 出现在两个已知状态之间（commit、数据集、版本），自动化「在状态 X 启动、检查、重复」，让你能 `git bisect run`。
9. **差分循环。** 把同一输入跑过旧版 vs 新版（或两份配置），diff 输出。
10. **HITL bash 脚本。** 最后手段。如果必须有人类点击，用 `scripts/hitl-loop.template.sh` 驱动_他们_，让循环仍然结构化。捕获的输出反馈给你。

建对反馈回路，bug 就修好了 90%。

### 收紧回路

把回路当产品对待。一旦有_一条_回路，就**收紧**它：

- 能更快吗？（缓存设置、跳过无关初始化、缩小测试范围。）
- 信号能更锐利吗？（断言具体症状，而不是「没崩」。）
- 能更确定吗？（钉住时间、播种 RNG、隔离文件系统、冻结网络。）

30 秒的 flaky 回路比没有强不了多少；2 秒的确定性回路是紧的——调试超能力。

### 非确定性 bug

目标不是干净复现，而是**更高的复现率**。把触发循环 100 次、并行化、加压、收窄时序窗口、注入 sleep。50% 概率 flake 的 bug 可以调试；1% 不行——持续提高复现率直到可调试。

### 当你真的建不出回路

停下并明确说出来。列出你试过的。向用户要：(a) 复现环境的访问权，(b) 捕获的工件（HAR 文件、日志 dump、core dump、带时间戳的录屏），或 (c) 加临时生产插桩的许可。**不要**在没有回路的情况下继续假设。

### 完成标准 —— 一条能变红的紧密回路

阶段 1 完成当回路**紧**且**能变红**：你能说出**一条命令**——脚本路径、测试调用、curl——而且你已经**至少运行过一次**（贴出调用和输出），并且它满足：

- [ ] **能变红** —— 它驱动真实 bug 代码路径并断言**用户的精确症状**，所以它能在这个 bug 上变红、修好后变绿。不是「运行不报错」——必须能_抓住这个具体 bug_。
- [ ] **确定性** —— 每次运行同样结论（flaky bug：按上文钉住的高复现率）。
- [ ] **快** —— 秒级，不是分钟级。
- [ ] **agent 可运行** —— 能无人值守运行；人类在环里只能通过 `scripts/hitl-loop.template.sh`。

如果你发现自己在这条命令存在之前读代码构建理论，**停下——直接跳到假设正是这个技能要防止的失败。** 没有能变红的命令，就没有阶段 2。

## 阶段 2 —— 复现 + 最小化

运行回路。看着它变红——bug 出现了。

确认：

- [ ] 回路产生**用户**描述的失败模式——不是碰巧在附近的另一个失败。错的 bug = 错的修复。
- [ ] 失败可跨多次运行复现（或对非确定性 bug，复现率足够高到可以对着调试）。
- [ ] 你捕获了精确症状（错误消息、错误输出、慢的时序），后续阶段能验证修复确实解决了它。

### 最小化

一旦变红，把复现缩小到**仍然变红的最小场景**。一次砍掉一个输入、调用者、配置、数据、步骤，每次砍完重跑回路——只保留对失败承重的部分。

为什么费这个劲：最小复现缩小了阶段 3 的假设空间（留下的可疑活动部件更少），并成为阶段 5 里干净的回归测试。

完成当**每个剩余元素都承重**——去掉任何一个都会让回路变绿。

在复现**并**最小化之前不要继续。

## 阶段 3 —— 假设

测试任何假设之前先产生 **3–5 个排好序的假设**。单假设生成会锚定在第一个看似合理的想法上。

每个假设必须**可证伪**：说出它做出的预测。

> 格式：「If <X> is the cause, then <changing Y> will make the bug disappear / <changing Z> will make it worse.」

如果你说不出预测，这个假设只是种感觉——丢弃或磨锐它。

**测试前把排序列表给用户看。** 他们常有瞬间重新排序的领域知识（「我们刚部署了 #3 的改动」），或知道他们已经排除的假设。便宜的检查点，省时间。别阻塞——用户离席就按你的排序继续。

## 阶段 4 —— 插桩

每个探针必须对应阶段 3 的一个具体预测。**一次只改一个变量。**

工具偏好：

1. 环境支持就用**调试器 / REPL 检查**。一个断点胜过十条日志。
2. 在能区分假设的边界加**定向日志**。
3. 绝不要「记录一切再 grep」。

**给每条调试日志打唯一前缀**，例如 `[DEBUG-a4f2]`。收尾清理变成一次 grep。无标记的日志活下来；有标记的日志死掉。

**性能分支。** 对性能回归，日志通常是错的。改为：先建立基线测量（计时 harness、`performance.now()`、profiler、查询计划），然后二分。先测量，后修复。

## 阶段 5 —— 修复 + 回归测试

**修复之前**写回归测试——但只有存在**正确的接缝**时才写。

正确接缝是测试在调用点按真实出现方式驱动**真实 bug 模式**的接缝。如果唯一可用的接缝太浅（bug 需要多个调用者却只有一个调用者的测试、无法复现触发链条的单元测试），那里的回归测试给的是虚假信心。

**如果没有正确接缝，这本身就是发现。** 记下来。代码库架构阻止了 bug 被锁死。把它标记给下一阶段。

如果存在正确接缝：

1. 把最小化复现变成该接缝处的失败测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 对着原始（未最小化）场景重跑阶段 1 的反馈回路。

## 阶段 6 —— 清理 + 事后复盘

宣布完成前必须：

- [ ] 原始复现不再复现（重跑阶段 1 回路）
- [ ] 回归测试通过（或缺失接缝已被记录）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（grep 前缀）
- [ ] 临时原型已删除（或移到明确标记的调试位置）
- [ ] 被证实的假设写进 commit / PR 消息——让下一个调试者学到

**然后问：什么本可以阻止这个 bug？** 如果答案涉及架构变更（没有好测试接缝、调用者缠结、隐藏耦合），把细节交接给 `/improve-codebase-architecture` 技能。在修复落地**之后**再给建议，而不是之前——你现在比开始时掌握更多信息。
