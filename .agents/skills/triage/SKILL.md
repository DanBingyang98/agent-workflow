# Triage（分流）

让项目 issue tracker 上的 issue 走过一组小型 triage 角色状态机。

如果本仓库把外部 pull request 当作请求面（见 issue-tracker 配置），triage 也覆盖它们：**PR 是附带了代码的 issue**——同样的角色、同样的状态、同样的机器，只有下面标「for a PR」的几处差异。按 tracker 配置把裸 `#42` 解析成 issue 或 PR。

triage 期间发布到 issue tracker 的每条评论或 issue **必须**以下面这个免责声明开头：

```
> *This was generated by AI during triage.*
```

- [AGENT-BRIEF.md](AGENT-BRIEF.md) —— 如何写持久的 agent 简报

## 角色

两个**分类**角色：

- `bug` —— 有东西坏了
- `enhancement` —— 新功能或改进

五个**状态**角色：

- `needs-triage` —— 维护者需要评估
- `needs-info` —— 等待报告者提供更多信息
- `ready-for-agent` —— 完全明确，准备好给离席 agent
- `ready-for-human` —— 需要人类实施
- `wontfix` —— 不会处理

对 PR，同样状态对着附带的代码解读：`ready-for-agent` 表示已附简报、agent 应就 diff 采取下一步；`ready-for-human` 表示已准备好由人类合并。

每个被 triage 的 issue 应恰好携带一个分类角色和一个状态角色。如果状态角色冲突，标记出来并在做任何其它事之前问维护者。

这些是规范角色名——issue tracker 中实际使用的标签字符串可能不同。映射应该已经提供给你——如果没有，运行 `/setup-matt-pocock-skills`。

状态转换：未打标签的 issue 通常先到 `needs-triage`；从那里走向 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后 `needs-info` 回到 `needs-triage`。维护者可随时覆盖——标记看起来异常的转换，并在继续前询问。

## 调用

维护者调用 `/triage` 并用自然语言描述他们想要什么。解读请求并行动。示例：

- "Show me anything that needs my attention"
- "Let's look at #42"（issue 或 PR）
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## 展示需要关注的东西

查询 issue tracker，呈现三个桶，最旧的在前：

1. **未打标签** —— 从未被 triage。
2. **`needs-triage`** —— 评估中。
3. **`needs-info` 且报告者自上次 triage 备注后有活动** —— 需要重新评估。

PR 在范围内时，把外部 PR 也放进这些桶，每行标 `[PR]` 或 `[issue]`。发现只浮出*外部* PR（tracker 配置定义谁算外部）——协作者进行中的 PR 不是 triage 工作。这个过滤只用于发现；被明确指名的 PR 无论作者是谁都总是被 triage。

显示每项的数量和一行摘要。让维护者挑。

## Triage 一个具体 issue 或 PR

1. **收集上下文。** 读完整 issue 或 PR（正文、评论、标签、作者、日期；PR 还要 diff）。解析任何既有 triage 备注，避免重问已解决的问题。用项目的领域词汇表探索代码库，尊重所触及区域的 ADR。对代码库跑两项检查：(a) **冗余** —— 按领域概念（不只是请求的措辞）搜索请求行为的现有实现，并报告你查过哪里。如果找到，就是已实现的 `wontfix`（步骤 5）。(b) **先前拒绝** —— 读 `.out-of-scope/*.md`，浮出任何与这个请求相似的内容。

2. **建议。** 告诉维护者你的分类和状态建议及理由，外加与请求相关的简要代码库摘要——包括是否已实现。等指示。

3. **验证主张。** 在任何拷问之前，检查主张是否站得住。对 bug，按报告者的步骤复现它。对 PR，确认 diff 做了它声称的事——checkout 它，跑相关测试或命令。报告发生了什么：已确认（带代码路径）、失败、或信息不足（强烈的 `needs-info` 信号）。已确认的验证让 agent 简报强得多。

4. **拷问（如果需要）。** 如果请求需要充实，一起运行 `/grilling` 和 `/domain-modeling` 技能——一轮轮问题把它拷问成形，边决策落地边磨锐领域术语并就地更新 `CONTEXT.md`/ADR。

5. **应用结果：**
   - `ready-for-agent` —— 发 agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human` —— 结构同 agent 简报，但注明为什么不能委托（判断、外部访问、设计决策、手工测试）。
   - `needs-info` —— 发 triage 备注（模板见下）。
   - `wontfix` —— 关闭，评论取决于*为什么*：
     - **已实现** —— 代码库中已存在该变更。指出它在哪里；**不要**写进 `.out-of-scope/`（那个知识库给*被拒绝的*请求，不是已构建的）。
     - **被拒绝（bug）** —— 礼貌解释，然后关闭。
     - **被拒绝（enhancement）** —— 写进 `.out-of-scope/`，从评论链接它，然后关闭（[OUT-OF-SCOPE.md](OUT-OUT-OF-SCOPE.md)）。
   - `needs-triage` —— 应用角色。有部分进展时可加可选评论。

## 快速状态覆盖

如果维护者说「move #42 to ready-for-agent」，信任他们并直接应用角色。确认你将要做的（角色变更、评论、关闭），然后行动。跳过拷问。如果没走拷问会话就移到 `ready-for-agent`，问他们是否要写 agent 简报。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把拷问期间解决的一切都记进「established so far」，让工作不丢失。问题必须具体可行动，不要「please provide more info」。

## 恢复之前的会话

如果 issue 或 PR 上有既有 triage 备注，读它们，检查报告者是否回答了任何未决问题，并在继续前呈现更新后的画面。不要重问已解决的问题。
