# 测试驱动开发（TDD）

TDD 是 red → green 的循环。本技能是这个循环产出值得保留的测试的参考：好测试是什么、测试放哪里、反模式有哪些、循环的规则是什么。每一节在每一轮循环中都适用——在循环前和循环中查阅，而不是事后。

探索代码库时，读取 `CONTEXT.md`（如果存在），让测试命名和接口词汇与项目的领域语言一致，并尊重你所触及区域的 ADR。

## 好测试是什么

测试通过公共接口验证行为，而不是实现细节。代码可以彻底改变；测试不应该。好测试读起来像一份规范——「user can checkout with valid cart」告诉你确切存在什么能力——并且能在重构后存活，因为它不关心内部结构。

示例见 [tests.md](tests.md)，mock 指南见 [mocking.md](mocking.md)。

## 接缝——测试放哪里

**接缝（seam）** 是你测试所在的公共边界：在不深入内部的情况下观察行为的接口。测试放在接缝处，绝不针对内部实现。

**只在预先约定的接缝处测试。** 写任何测试之前，先写下要测试的接缝并与用户确认。未确认的接缝不写测试。你不可能测试一切——提前约定接缝，才能让测试精力落在关键路径和复杂逻辑上，而不是每个边缘用例。

要问：「公共接口是什么，我们应该测试哪些接缝？」

当接口本身的形态存疑时——模块该多深、接缝该在哪、接口该暴露什么——使用 `/codebase-design` 技能获取词汇。它是 module、interface、depth、seam、adapter、leverage、locality 等术语的共享来源，是一个按需查阅的参考，不是要运行的会话。

## 反模式

- **耦合实现（Implementation-coupled）**——mock 内部协作者、测试私有方法、或通过旁路验证（查询数据库而不是使用接口）。特征：重构时测试就挂，但行为没变。
- **同义反复（Tautological）**——断言用与代码相同的方式重算期望值（`expect(add(a, b)).toBe(a + b)`、用手工同法推导的快照、与自身相等的常量），所以它构造上必然通过、永远不可能与代码分歧。期望值必须来自独立的事实来源——已知正确的字面量、手算示例、规范。
- **水平切片（Horizontal slicing）**——先写全部测试，再写全部实现。批量测试验证的是_想象出来的_行为：你测试的是事物的_形状_而不是面向用户的行为，测试对真实变化不敏感，而且你在理解实现之前就锁定了测试结构。改成**垂直切片**——一个测试 → 一个实现 → 重复，每个测试都是一颗**曳光弹（tracer bullet）**，回应上一轮循环教给你的东西。

## 循环的规则

- **先红后绿（Red before green）。** 先写失败的测试，然后只写足够让它通过的代码。不要预想未来的测试，也不要加投机性功能。
- **一次一片。** 每轮循环一个接缝、一个测试、一个最小实现。
- **重构不属于循环。** 它属于审查阶段（见 `code-review` 技能），而不是 red → green 实现循环。
