# ADR 格式

ADR 住在 `docs/adr/`，用顺序编号：`0001-slug.md`、`0002-slug.md` 等。

需要第一个 ADR 时才惰性创建 `docs/adr/` 目录。

## 模板

```md
# {决策的短标题}

{1-3 句：上下文是什么、我们决定了什么、为什么。}
```

就这些。一条 ADR 可以是一个段落。价值在于记录*做了*那个决定和*为什么*——不是填满各个部分。

## 可选部分

只有真正增加价值时才包含。大多数 ADR 不需要。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——决策会被重访时有用
- **Considered Options（考虑过的选项）** —— 只有被拒的替代方案值得记住时
- **Consequences（后果）** —— 只有需要点出非显然的下游影响时

## 编号

扫 `docs/adr/` 找最高编号，加一。

## 何时提供 ADR

三条必须同时成立：

1. **难逆转** —— 以后改主意的成本有实际意义
2. **没有上下文会令人惊讶** —— 未来读者会看代码心想「他们到底为什么这么做？」
3. **真实取舍的结果** —— 存在真实替代方案，你出于具体原因选了其中一个

如果容易逆转，跳过——你反正会反悔。如果不令人惊讶，没人会疑惑。如果没有真实替代方案，除了「我们做了显而易见的事」没什么可记。

### 什么够格

- **架构形态。**「我们用 monorepo。」「写模型是事件溯源，读模型投影到 Postgres。」
- **context 之间的集成模式。**「Ordering 和 Billing 用领域事件通信，不是同步 HTTP。」
- **带锁定效应的技术选择。**数据库、消息总线、认证供应商、部署目标。不是每个库——只是换掉要花一个季度的那些。
- **边界和范围决策。**「Customer 数据由 Customer context 拥有；其它 context 只按 ID 引用。」显式的 no 和 yes 一样有价值。
- **对显而易见路径的刻意偏离。**「我们用手工 SQL 而不是 ORM，因为 X。」任何合理读者会假设相反做法的东西。这些阻止下一个工程师「修复」某个刻意为之的东西。
- **代码里看不见的约束。**「因为合规要求不能用 AWS。」「因为伙伴 API 契约，响应必须低于 200ms。」
- **拒绝原因非显然的替代方案。**如果你考虑过 GraphQL 而选了 REST 且理由微妙，记下来——否则六个月后又会有人建议 GraphQL。
